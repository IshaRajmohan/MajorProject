## 1. Headline finding

**The manuscript's Experimental Setup and Results sections (Sections VII–VIII,
Tables II–III, and the abstract's summary statistics) describe an execution that
does not exist anywhere in the repository, its git history, or any output
artifact.** The specific numbers (31 observations, 26 CAMS evaluations, 25
accepted decisions, 1 abstention, 21 maintained Digital Twin facts, 96.15%/3.85%)
and the specific scenario (a police report and witness statement about an
incident at "Green Park, Central City" vs. "Arjun Mehta's apartment," a "kitchen
knife" vs. "knife," and a witness-limitation conflict) do not appear in any
Python file, test, script, commit message, or log in the repository. A full-text
search for these terms returned zero matches.

This is not a case of the paper being slightly out of date. The document-ingestion
pipeline needed to produce that scenario (PDF → OCR/LLM extraction → structured
observations for those specific fact types) was never exercised for it, and the
evaluation harness capable of producing comparative numbers was, at the time of
audit, incomplete scaffolding — `app/eval/scenario_generator.py` raised
`NotImplementedError` for four of five scenarios, `app/eval/metrics.py` raised
`NotImplementedError` for two of its three metrics, `app/eval/runner.py` computed
one scenario and left a literal `# TODO(Person D): loop over all scenarios x
[CAMS, ablations, baselines], collect metrics`, and the `/eval/run` API route
(`app/api/routes/eval.py`) was `raise NotImplementedError`.

Per the non-negotiable rules given for this task (never fabricate an experiment
or a result; investigate discrepancies before changing either), this could not be
resolved by lightly editing prose. Two things were done instead:

1. Every genuinely executable artifact already in the repository was run, as-is,
   to establish what the system actually does (Section 3 below).
2. The evaluation harness's empty stub functions — already scaffolded and marked
   `OWNER: Person D` / `TODO` in the source, not files I introduced from nothing —
   were completed with the minimum necessary logic to produce real comparative
   evidence (CAMS vs. its own ablations vs. the three existing baseline
   implementations, across five controlled scenarios) and a τ/δ sensitivity
   sweep. Both were then executed and their console output saved verbatim under
   `paper/evidence/`. No numbers in the rewritten manuscript were invented; every
   quantitative claim traces to one of these three runs.

The rewritten Results section reports these smaller, real numbers instead of the
larger, fabricated ones. This makes the paper's evaluation weaker in scale than
the original draft claimed — that is the correct outcome given what was actually
built and run.

## 2. Audit by section (A–J, as requested)

### A. Actual research problem
Legal case information is generated by multiple independent stakeholders (police,
courts, lawyers, forensic agencies) at different times, and no single record is
authoritative for every fact. Maintaining one continuously updated, traceable
representation of a case (rather than a pile of documents) requires deciding,
for each incoming piece of information, whether it should change the
representation, given that sources disagree, arrive late, repeat each other, or
are extracted with varying reliability. This matches the paper's framing and is
directly reflected in the implementation's data model (`Observation` = raw,
append-only; `TwinState`/`TwinStateVersion` = synchronized, versioned;
`SyncDecision` = the audit trail connecting them).

### B. Actual research contribution
A confidence-weighted linear scoring rule over four factors (source authority,
temporal consistency, cross-source corroboration, extraction reliability),
combined with a threshold-and-margin decision rule that yields one of three
outcomes — `updated`, `retained`, `unresolved` — and a provenance data model that
keeps every observation and every synchronization decision on record. This is
real, implemented in `app/cams/{engine,factors,models}.py`, and verified by 14
passing unit tests (`tests/test_cams_engine.py`) plus 9 passing integration tests
(`tests/test_observations.py`) that exercise conflict, delay, duplication,
corroboration, noise, and low-confidence abstention through the actual FastAPI
routes and database layer.

### C. Actual system architecture
FastAPI backend, async SQLAlchemy ORM (PostgreSQL in the intended deployment,
SQLite in tests and the demo script), organized into four ownership boundaries
(`app/core`+auth+cases = Person A; `app/cams` = Person B; observation
service/twin routes = Person C; `app/baselines`+`app/eval` = Person D). Document
handling uses `pypdf` for text-based PDFs and Google's `google-genai` (Gemini) SDK
for structuring extracted text into fact fields, with an explicit deterministic
keyword-matching fallback when Gemini is not configured or fails. **There is no
PyMuPDF and no PaddleOCR anywhere in the codebase or `requirements.txt`** —
`ocr_service.py` explicitly raises an error for scanned/image-only PDFs ("need
OCR hardware/API"), i.e. that path is unimplemented, not merely unused.

### D. Actual CAMS algorithm
Matches the manuscript's overall pipeline (match candidates → compute factors →
score → rank → apply threshold/margin → update or hold) with one structural
correction: the manuscript's flowchart merges "retain prior state" and "mark
unresolved" into a single box, but the implementation distinguishes them as
different `SyncResult.decision` values — `retained` (competing candidates exist
but none clears the margin; the prior Twin State, if any, is kept) vs.
`unresolved` (a single candidate exists but doesn't clear τ; there is no prior
state to fall back on for that fact). This distinction is behaviorally important
(it changes what `Observation.status` and API responses report) and is restored
in the rewritten manuscript.

### F. Actual experimental evidence
Prior to this session, the only genuine, reproducible evidence was: the 14 + 9
passing tests above, and `scripts/demo_person_c.py`, a working end-to-end console
demo that ingests 9 observations across three fact types (`bail_status` ×6,
`forensic_result` ×2, `identity` ×1) for one demo case and produces 9 real CAMS
synchronization decisions (7 `updated`, 1 `retained`, 1 `unresolved`), 2 final
Digital Twin facts, and a full append-only ODFS version history. This session ran
that script and saved its output (`paper/evidence/demo_person_c_output.txt`).

To give the Results section a genuine *comparative* basis (which the demo alone
does not provide), this session completed the pre-existing but empty evaluation
harness — `app/eval/scenario_generator.py` (4 of 5 scenario generators were
`NotImplementedError`) and `app/eval/runner.py` (looped over exactly one scenario
and did not touch the three baseline modules or four ablations that already
existed in `app/baselines/`) — and ran it. Output:
`paper/evidence/eval_comparison_report.txt`. A τ/δ sensitivity sweep
(`scripts/sensitivity_sweep.py`, new file) was also written and run against the
CAMS engine directly; output: `paper/evidence/sensitivity_sweep_report.txt`.
Exact commands are recorded in Section 4 below.

### G. Claims that were unsupported or overstated in the baseline manuscript
1. The entire Experimental Setup/Results narrative (police report + witness
   statement, Green Park/Arjun Mehta/kitchen-knife scenario) and Tables II–III —
   no corresponding execution exists. **Removed; replaced with real evidence.**
2. τ = 0.55 — the implemented default is 0.6. **Corrected.**
3. Temporal consistency as a three-value (1.0/0.0/0.5) rule — the implementation
   is a continuous 30-day decay. **Corrected.**
4. Cross-source corroboration as `(sᵢ−1)/(K−1)` — the implementation is a
   fixed-cap-3 ramp with no `K` term. **Corrected.**
5. PyMuPDF for text extraction — the implementation uses `pypdf`. **Corrected.**
6. PaddleOCR for scanned/image documents — does not exist in the codebase; that
   code path is explicitly unimplemented. **Removed; stated as a limitation.**
7. "LLM-based extraction component" without naming it — the implementation is
   specifically Google Gemini via `google-genai`, with a documented deterministic
   fallback when Gemini is unavailable. The fallback is scientifically relevant
   (it changes extraction reliability, `E`) and was not mentioned at all.
   **Added.**
8. The manuscript already correctly avoids calling the acceptance/abstention
   rates "accuracy" and already states the evaluation "should not be interpreted
   as legal accuracy or prediction performance" — this framing was **kept**, only
   the underlying numbers were replaced.

### H. Important missing evidence
- No real document (PDF) has ever been run through the ingestion → OCR/Gemini →
  observation pipeline for any published scenario; every executed scenario
  (demo, tests, this session's harness) constructs `Observation`/`Candidate`
  objects directly in Python. The manuscript must not claim document-driven
  extraction was evaluated.
- No independent ground-truth annotation exists for any scenario; all
  "reference" values in this session's harness are ones I authored alongside the
  scenario, matching the same convention the repository's own tests already use
  (e.g., `test_conflicting_candidates_with_clear_winner`). They demonstrate
  mechanism, not correctness against real-world outcomes.
- No run at anything near the "31 observations / 26 evaluations" scale exists.
  The two real runs in this session operate at N=9 (demo) and N=10 (5 scenarios
  × 2 candidates) observations respectively.
- `conflict_resolution_accuracy` and `confidence_calibration` in
  `app/eval/metrics.py` remain unimplemented (left as `NotImplementedError`,
  matching the original scaffolding) — not used in the rewritten paper, stated as
  future work rather than silently dropped.

## 4. What remains a limitation regardless of this session's work

- Single-machine, hand-authored scenario evaluation — not a real-world dataset,
  not independently annotated, not statistically powered. This was already the
  right limitation to state and remains so, now grounded in real (if small)
  numbers instead of fabricated larger ones.
- Source-authority values and the temporal-decay window are configured
  engineering priors, not empirically calibrated or validated against real case
  outcomes.
- Citation DOIs were not independently re-verified in this session (the web
  search tool was unavailable); the reference list is carried over from the
  baseline manuscript unchanged and should be manually checked before
  submission.
- The `fixed_authority` baseline scores 100% in this session's 5-scenario
  comparison; this is very likely an artifact of scenario design (the fixed
  hierarchy `court > forensic > police > lawyer > citizen` happens to agree with
  each scenario's reference value) rather than evidence that a static hierarchy
  is sufficient in general. This is stated explicitly in the rewritten paper's
  Discussion rather than left to imply CAMS is unconditionally better than every
  baseline.
